## 二、各角色业务流程入口

### 2.1 集团领导 (executive) — 王总

**可访问页面**: 62 页（全部经营分析+业务台账+结算，不含 WK-01/WK-03/GS-02/CF 配置）

**可执行 action**:
| Action | 入口 | 说明 |
|--------|------|------|
| `review` | 审批页 | 审批超概算预算/重大变更（`requiredRole: 'executive'`） |
| `review-management` | 高管审批页 | 审批重大风险处置/未签额外投入/验收异常/结算争议 |
| `review-early-investment` | 提前投入审批 | 审批提前投入申请 |
| `decide-initiation` | 立项决策 | PMC决策会节点审批（重大/特大型立项） |
| `review-project-change` | 变更审批 | 审批已分级的变更（`requiredRole: 'executive'`） |

**分支与异常处理**:
- 预算审批：超概算时 `requiredRole` 自动升级为 `executive`，否则由 PMO 审批
- 变更审批：PMO 分级后根据规则决定 `requiredRole` 为 `executive` 或 `pmo`
- 立项决策：仅在 `path === 'PMC决策会'` 时进入，`path === '线上会签'` 时由 PMO 决策
- 敏感字段可见：`margin`、`evaluation`、`contact`（不可编辑 `labor-rate`）

**问题**: ⚠️ `review-project-change` 在 `defaultActions` 中未列出，但在 `business-domain.ts` 的 `review` handler 中通过 `approval.requiredRole` 动态判断。这意味着 executive 的 action 白名单中缺少 `review-project-change`，但通过 `review` action 间接覆盖。**逻辑正确但白名单不完整。**

### 2.2 PMO负责人 (pmo) — 李主任

**可访问页面**: 68 页（最多，含 CF-01/02/03/04/06 配置页）

**可执行 action**: 40+，覆盖全流程监管

| 流程阶段 | Action | 说明 |
|---------|--------|------|
| 立项 | `assess-initiation-risk`、`classify-initiation`、`decide-initiation`、`sign-initiation`、`resume-initiation` | 风险评估→分级→决策 |
| 预算 | `review`、`confirm-budget-baseline`、`review-planning` | 审批预算（非超概算时）、确认基线 |
| 执行 | `stage-gate`、`review-plan`、`update-ticket`、`quality-check` | 阶段门禁、计划变更审批 |
| 变更 | `classify-project-change`、`review-project-change`、`review` | 变更分级、审批 |
| 验收 | `review-acceptance`、`confirm-acceptance` | 内部/供应商验收办理 |
| 结算 | `review-settlement` | 结算审批 |
| 收尾 | `start-post-evaluation`、`confirm-post-evaluation`、`review-archive-file`、`confirm-project-archive` | 后评价、归档 |
| 运维 | 全部 `operations` actions | 运维全生命周期 |
| 配置 | `configuration-save/publish/apply-template`、`finance-config-save/publish` | 系统配置 |

**分支与异常处理**:
- 立项：`assess-initiation-risk` → 风险评分 → `classify-initiation` → 自动决定 `path`（线上会签/PMC决策会）
- 变更：`classify-project-change` → 根据规则决定 `requiredRole`（pmo/executive）
- 阶段门禁：`stageChecks()` 检查全部条件，任一不通过则拒绝
- 计划变更：`review-plan` 支持多角色会签（`requiredRoles`），全部通过才生效
- 暂缓立项：`resume-initiation` 可恢复暂缓申请

**问题**: ⚠️ PMO 的 `defaultActions` 包含 `create-ticket`，但 `canAccessAction` 中额外要求 PMO 必须是项目成员。**PMO 通常不是项目成员，此条件可能导致 PMO 无法创建事项。** 但 PMO 可以通过 `update-ticket` 更新已有事项。

- `submit-acceptance`：仅主PM可发起验收
- `save-settlement`：仅主PM或市场可编制结算

**问题**: ⚠️ `update-forecast` 在 `defaultActions` 中未列出，但在 `business-domain.ts` 中有完整 handler。**项目经理无法通过权限白名单执行此 action。** 这是之前新增功能时遗漏的。

## 三、发现的问题汇总

### 🔴 问题 1：`update-forecast` 未加入 action 白名单

**文件**: `src/mock/configuration-access.ts`

`update-forecast` 在 `business-domain.ts` 中有完整 handler（requireRole + 校验），但未加入任何角色的 `defaultActions` 白名单。`assertActionAccess` 会拦截此 action。

**影响**: 项目经理无法通过 UI 执行 `update-forecast`（之前新增功能时遗漏）

**修复**: 在 `project-manager` 的 `defaultActions` 中添加 `'update-forecast'`

---

### 🔴 问题 2：`review-project-change` 未在 executive 白名单中

**文件**: `src/mock/configuration-access.ts`

executive 的 `defaultActions` 包含 `review`，变更审批通过 `review` handler 的 `approval.requiredRole` 动态判断。但 `review-project-change` 本身未在 executive 白名单中。

**影响**: 如果 PMO 分级后 `requiredRole` 为 `executive`，executive 可以通过 `review` action 审批，但 `review-project-change` action 本身被白名单拦截。

**修复**: 在 executive 的 `defaultActions` 中添加 `'review-project-change'`

---

### 🔴 问题 3：`confirm-cost(maintenance=true)` 死分支

**文件**: `src/mock/business-domain.ts:396-400`

```typescript
if (action.maintenance) {
  throw new Error('运维费用请通过周期原单填报和财务审核入口，不允许直接入账');
```

`maintenanceCosts` 字段永远无法写入，但仍在 `BusinessState` 中。

**影响**: 死代码，无实际业务影响

### 🟡 问题 4：PMO 的 `create-ticket` 需要项目成员关系

**文件**: `src/mock/configuration-access.ts` 的 `canAccessAction`


PMO 通常不是项目成员，`memberIds` 可能不包含 PMO 用户 ID。

**影响**: PMO 可能无法在非本人参与的项目中创建事项

---

### 🟡 问题 5：solution-tech 数据范围 `self` 限制

**文件**: `src/mock/configuration-access.ts`

solution-tech 的 `dataScope: 'self'`，且 `projectRelationRequired: true`。如果赵工未加入某项目团队，将无法访问该项目。

**影响**: 方案架构师可能无法查看全部在建项目的技术方案

---

### 🟡 问题 6：market 的 `save-settlement` 权限

market 的 `defaultActions` 包含 `save-settlement`，但 `settlement.ts` 中检查 `pm || actor.role !== 'market'`。market 角色可以编制结算，但结算通常应由 PM 或财务处理。

**影响**: 权限合理但边界模糊

## 五、异常处理覆盖情况

| 异常场景 | 处理方式 | 覆盖 |
|---------|---------|:----:|
| 预算超概算 | `requiredRole` 自动升级为 executive | ✅ |
| 变更超权限 | PMO 分级后决定审批层级 | ✅ |
| 立项风险评分不足 | 综合等级不得低于矩阵最高风险 | ✅ |
| 立项分级过低 | 不能降低规则最低项目级别 | ✅ |
| 阶段门禁不通过 | 列出全部失败条件 | ✅ |
| 计划变更超30天 | 需财务+PMO 双签 | ✅ |
| 同一来源重复入账 | 拒绝重复成本 | ✅ |
| 承诺余额不足 | 拒绝结转 | ✅ |
| 任务进度回退 | 拒绝 | ✅ |
| 未完成任务填完成时间 | 拒绝 | ✅ |
| 结算材料退回 | 支持整改流程 | ✅ |
| 验收整改 | 支持回复流程 | ✅ |
| 暂缓立项恢复 | PMO 凭复评说明恢复 | ✅ |
| 权限策略锁死管理员 | 强制保留管理员入口 | ✅ |
| 敏感字段脱敏 | 按策略脱敏审计日志 | ✅ |
