## 1. 商机→立项数据流

### 1.1 商机状态流转

```
草稿 ──(save-opportunity, submit=true)──→ 待评估
待评估 ──(start-opportunity-assessment)──→ 待评估（评估中）
待评估 ──(conclude-opportunity, conclusion='跟进中')──→ 跟进中
跟进中 ──(conclude-opportunity, conclusion='拟立项')──→ 拟立项
拟立项 ──(conclude-opportunity, conclusion='方案评审中')──→ 方案评审中
方案评审中 ──(方案评审通过 + 概算冻结)──→ 已转立项
```

**文件**: `src/mock/opportunities.ts` → `applyOpportunityAction()`

**字段映射**:
- `Opportunity.status` 直接控制状态流转
- `OpportunityMeta.assessments[]` 记录评估轮次
- `Opportunity.currentEstimateVersionId` 关联冻结概算

### 1.2 概算编制→冻结

```
estimate-create-draft → estimate-save-draft → estimate-publish → estimate-freeze
```

**文件**: `src/mock/estimates.ts`

**关键规则**:
- 概算冻结后 `EstimateVersion.isFrozen = true`
- 冻结概算通过 `Opportunity.currentEstimateVersionId` 关联到商机
- 冻结后商机进入 `opportunityLocked` 状态，基础信息不可修改

### 1.3 已转立项→立项申请→评审→正式项目

```
已转立项 → save-initiation → submit-initiation → assess-initiation-risk
→ classify-initiation → sign-initiation(会签) → decide-initiation(通过)
→ createInitiatedProject()
```

**文件**: `src/mock/initiation.ts` → `applyInitiationAction()`

**数据从 Opportunity 到 Project 的字段映射**:

| Opportunity 字段 | Project 字段 | 转换逻辑 |
|---|---|---|
| `name` (去掉"商机"后缀) | `name` | `name.replace(/商机$/,'')` |
| `customerId/customerName` | `customerId/customerName` | 直接继承 |
| `departmentId/departmentName` | `departmentId/departmentName` | 直接继承 |
| `estimatedAmount` | `revenueAmount` | 作为预计收入 |
| `currentEstimateVersionId` | `frozenEstimateVersionId` | 冻结概算版本 |
| `id` | `opportunityId` | 关联回源 |
| — | `contractAmount` | 已签合同金额，否则为 0 |
| — | `isUnsigned` | `!contract`（未签合同） |
| — | `phase: '立项'` | 固定初始阶段 |
| — | `subPhase: 'WBS编制'` | 固定初始子阶段 |

**文件**: `src/mock/initiation.ts:createInitiatedProject()`

### 1.4 提前投入成本继承

```
inheritEarlyCosts(state, o.id, id)
```

**文件**: `src/mock/early-investments.ts`

**逻辑**: 将商机 `earlyCosts` 中 `opportunityId === o.id` 的成本记录复制到项目的 `costs` 数组中，`projectId` 更新为新项目 ID。

### 1.5 发现问题

| # | 问题 | 严重度 |
|---|------|--------|
| O-1 | `createInitiatedProject` 中 `pmId: ''`、`pmName: '待任命'`，但 `memberIds: []`。项目创建后 PM 为空，需后续通过 `nominate-pm` 任命。但 `memberIds` 为空数组意味着权限判断可能失效 | 🟡 |
| O-2 | 立项通过后 `o.status='已转立项'`，但如果项目被否决，`o.status='已终止'`。没有"重新立项"的路径——已终止的商机无法恢复 | 🟡 |
| O-3 | `initiationSource()` 中 `earlyCostTotal` 和 `earlyCostSources` 从商机继承到立项快照，但 `createInitiatedProject` 中 `inheritEarlyCosts` 是独立调用，两者可能不一致 | 🟢 |

## 2. 立项→执行数据流

### 2.1 预算基线冻结流程

```
submit-planning → review-planning(通过) → submit-budget-draft
→ submit-budget → review(审批通过) → confirm-budget-baseline
```

**文件**: `src/mock/budget.ts`、`src/mock/budget-drafts.ts`

**关键步骤**:
1. **WBS 编制**: `save-planning` → `submit-planning` → `review-planning`
2. **预算编制**: `save-budget-draft` → `submit-budget-draft`（自动调用 `submit-budget`）
3. **预算审批**: `submit-budget` → `review`（PMO 或 executive）→ `confirm-budget-baseline`（PMO）

### 2.2 基线冻结对项目的影响

`confirmBudgetBaseline()` 更新以下项目字段:

| 字段 | 值 |
|---|---|
| `budgetAmount` | `budget.totalAmount` |
| `currentBaselineVersion` | `V{version}.0` |
| `costVariance` | `rollingCost - budgetAmount` |
| `costVarianceRate` | `percentage(costVariance, budgetAmount)` |

同时:
- 将 `BudgetVersion` 标记为 `'已生效'`
- 创建 `BaselineVersion` 记录完整快照
- 将 `PlanningDraft` 标记为 `'已冻结'`
- 将 WBS 任务和里程碑写入 `state.tasks` 和 `state.milestones`

### 2.3 阶段门控

```
stage-gate → 检查阶段条件 → 更新 phase/subPhase
```

**文件**: `src/mock/stage.ts`

**逻辑**: `stageChecks()` 检查当前阶段的前置条件是否满足，通过后更新 `project.phase` 和 `project.subPhase`。

### 2.4 发现问题

| # | 问题 | 严重度 |
|---|------|--------|
| E-1 | `confirmBudgetBaseline` 中 `state.budgets.filter(b=>b.projectId===p.id&&(b.status==='已生效'||b.id==='BUD-PENDING-${approval.id}')).forEach(b=>{b.status='已废弃'})` — 将所有已生效预算标记为废弃，但如果有多个已生效预算（异常状态），会全部废弃 | 🟢 |
| E-2 | 首次基线冻结时 `state.tasks.push(...)` 和 `state.milestones.push(...)`，但后续变更基线时不会重复 push（通过 `if(!baseline)` 判断）。这意味着变更批准后 WBS 任务通过 `changes.ts` 中的 `r.proposed.tasks` 直接替换 | 🟡 |
| E-3 | `submit-budget` 在 `business-domain.ts` 中直接处理（不在 `applyBudgetPlanningAction` 中），而 `submit-budget-draft` 在 `budget-drafts.ts` 中处理。两个入口都调用 `transition(state,{type:'submit-budget',...})`，但 `submit-budget-draft` 先验证再递归调用，`submit-budget` 直接处理。逻辑分散在两个文件中 | 🟢 |

## 3. 执行→变更数据流

### 3.1 变更流程

```
save-project-change → submit-project-change → assess-project-change(技术/财务/市场)
→ classify-project-change(PMO分级) → review-project-change(审批)
```

**文件**: `src/mock/changes.ts` → `applyProjectChangeAction()`

### 3.2 变更批准后的数据更新

`review-project-change` 批准后:

| 项目字段 | 更新值 |
|---|---|
| `plannedEndDate` | `r.proposed.plannedEndDate`（工期调整） |
| `revenueAmount` | `r.input.proposedIncome`（收入调整） |
| `progressRate` | 重新计算（基于任务完成率） |
| `currentBaselineVersion` | `BASE-{approval.id}`（通过 `confirmBudgetBaseline`） |

同时:
- WBS 任务替换: `state.tasks = state.tasks.filter(...).concat(r.proposed.tasks.map(...))`
- 里程碑替换: 保留已达成里程碑的状态，更新未达成里程碑的计划日期
- 团队资源更新: `state.projectTeams[p.id].members = structuredClone(r.proposed.resources)`
- 创建新的 `Approval` 记录

### 3.3 发现问题

| # | 问题 | 严重度 |
|---|------|--------|
| C-1 | `review-project-change` 中 `confirmBudgetBaseline` 被调用，但 `changes.ts` 中的 `confirmBudgetBaseline` 来自 `budget.ts`，它期望 `approval.baseline.snapshot` 存在。变更的 `snapshot` 来自 `r.proposed`，但 `confirmBudgetBaseline` 中会检查 `state.baselines.find(b=>b.projectId===p.id&&b.status==='已生效')?.id !== approval.baseline.id`。如果基线在变更审批期间被其他操作修改，会抛出"源基线已变化"错误 | 🟢 |
| C-2 | `assess-project-change` 需要 3 个专业角色（技术/财务/市场）都提交评估后才能进入 `待分级`。但如果某个角色不需要（如简单变更），没有跳过机制 | 🟡 |
| C-3 | `financeSignoff` 字段已添加，`changes.ts` 中已实现强制检查——成本/资源变更审批前必须完成财务会签 | ✅ 已修复 |

## 6. 成本归集与四算联动数据流

### 6.1 成本订单流程

```
submit-cost-order → process-cost-order(approve) → process-cost-order(progress)
→ process-cost-order(accept) → process-cost-order(book)
```

**文件**: `src/mock/cost-orders.ts` → `applyCostOrderAction()`

### 6.2 成本入账后的数据更新

`process-cost-order(book)` 执行后:

| 项目字段 | 更新值 |
|---|---|
| `actualCost` | `actualCost + amount` |
| `commitmentBySubject[subjectId]` | `-= amount`（释放承诺） |
| `committedCost` | 重新计算 |
| `rollingCost` | `actualCost + committedCost + forecastRemainingCost` |
| `costVariance` | `rollingCost - budgetAmount` |
| `costVarianceRate` | `percentage(costVariance, budgetAmount)` |

同时创建 `CostItem` 记录。

### 6.3 四算联动

`selectFourCalculations()` 计算四算金额:

```
概算金额 = EstimateVersion.totalCost（来自冻结概算）
预算金额 = BudgetVersion.totalAmount（来自生效预算）
核算金额 = sum(CostItem.amount) + committedCost + forecastRemainingCost
结算金额 = SettlementRecord.finalCost（来自锁定结算）
```

**文件**: `src/mock/selectors.ts` → `selectFourCalculations()`

### 6.4 成本超支预警

`selectConfiguredHealth()` 检查成本偏差:
- `costVarianceRate > 0` → 超支预警
- 结合 `health` 状态（green/yellow/orange/red）

### 6.5 日报/周报与成本关联

日报和周报通过 `ReportSnapshot` 捕获成本快照:
```
ReportSnapshot = {
  budget: p.budgetAmount,
  actualCost: p.actualCost,
  rollingCost: p.rollingCost,
  ...
}
```

**文件**: `src/mock/reports.ts` → `reportSnapshot()`

### 6.6 发现问题

| # | 问题 | 严重度 |
|---|------|--------|
| K-1 | `costAvailability()` 中 `assertNewProjectCommitment(state,p)` 检查未签项目额度，但 `autoBlocked` 字段从未被检查。超限后不会阻止新的成本订单 | 🔴 |
| K-2 | `process-cost-order(book)` 中 `adjustCommitment(o.subjectId, -o.amount)` 释放承诺，但如果 `commitmentBySubject` 尚未初始化（`??=`），会使用 `selectFourCalculations` 的当前值。如果入账金额超过承诺金额，`commitmentBySubject[subjectId]` 可能变为负数 | 🟡 |
| K-3 | 日报 `actualHours` 字段已添加，日报填报 Modal 中工时输入框的保存逻辑已与 `DailyReport.actualHours` 关联 | ✅ 已修复 |
| K-4 | `selectFourCalculations` 中 `commitmentBySubject` 和 `forecastBySubject` 的分配逻辑：如果项目没有设置这两个字段，使用 `allocateMoney` 按预算比例分配。这可能导致与实际承诺/预测不一致 | 🟢 |
