### 1.2 范围边界

- 本期补齐建设期四类事项及其项目、日报、质量、变更、待办、验收、归档入口出口。沿用HS-05～08四个逻辑页面，复用统一台账/详情组件，不新增一套独立工单事实库。
- 运维事件继续由`operationEvents`及运维周期管理；可提供来源关联和跳转，不能把建设期事项直接改造成运维事件。依据：功能§5.7 JS-043～045、PRD§12.18～20、§24.10。
- 售前调研、立项风险报告、审批整改、WBS任务、验收整改本身不是四类工单。原文要求关联/整改闭环，并未要求所有对象强制改成工单；需要统一督办时建立来源引用，保留各域主事实。
- 真实消息平台、真实文件服务器、外部客服门户、通用ITSM/SLA派单中心不在四份原文的四类事项页面范围。原型可演示提醒和文件版本元数据，真实集成另行约定。

## 4. 页面规划与验收要点

## 5. 数据模型与状态机建议

### 5.1 保持单一事实的增量模型

保留`BusinessState.requirements/bugs/issues/risks`为各类主记录，`ticketMeta[id]`只保存主记录未承载的扩展信息。`TicketView`为selector返回的只读判别联合视图，禁止另建`tickets[]`、页面独立项目/审批/成本副本。现有重复期限/姓名显示字段需明确主值来源，由transition一次同步兼容投影，不能两个入口分别编辑。

| 层次 | 建议字段/规则 | 对应要求 |
|---|---|---|
| 公共身份 | id/code、kind（视图判别）、projectId；creatorId/ownerId为身份键，姓名仅显示/历史快照 | T02/T06/T19 |
| 公共元数据 | description/category、createdAt、deadline、resolvedAt、closedAt、resolution、solution、confirmationComment；未知历史可空并注明来源 | T02/T07/T14/T18 |
| 需求 | priority、businessValue、productLineId/name、productId/name、wbsIds、impactScope/impactBudget/impactSchedule；旧product保留legacyProduct | T03/T04 |
| BUG | severity、priority、reproductionSteps、expectedResult、actualResult、environment、fixVersion、plannedFixAt、actualFixAt、verifierId；最终关闭仍按发起人规则，验证人不自动取代发起人 | T05/T07 |
| 风险 | probability/impact、level（按规则计算）、strategy、measures、measureDueAt（默认共用deadline）、assessedAt/By、riskRuleVersion、occurredAt；转出问题ID由fromRiskId反查或原子维护 | T10～13 |
| 问题 | severity、impactScope、latestProgress/solution、fromRiskId；quality/acceptance/report来源通过typed sourceRefs关联 | T14/L03～06 |
| 变更关联 | changeRefs: { kind: planRequest或projectChange, id }[]；适用变更种类与批准/生效结果从原对象读取 | T04/L05 |
| 附件与轨迹 | attachmentRefs: 文档ID+版本；history增加稳定eventId、actorId/role、时间、动作、前后状态、意见及附件引用；只追加 | T06/T07/L11 |
| 升级 | escalationEvents/当前层级引用、ruleVersion、sourceId；待办及决策关联源事项ID，保证幂等 | T13/T17/L07 |
| 运维引用 | 可选建设事项sourceRef→运维事件；运维主事实仍在operationEvents并带operationId/projectId | L09 |

不要用当前日期回填未知真实创建/修复日。演示时钟继续统一使用AS_OF_DATE/既有基准日机制；超期和提醒由公共规则计算，不由页面各算一套。

### 5.2 状态与转换

沿用当前中文状态名称；下面的额外约束为建议补强，并非新增原文状态。所有操作检查页面策略、动作策略、项目范围、对象责任、状态、归档限制；统一锁定口径待Q7决定。

| 类型 | 转换 | 触发者与条件 |
|---|---|---|
| 需求 | 新建→待处理；反馈开工→开发中；提交解决→待验证 | 有权项目发起人新建；责任人或获授权主PM处理；涉及范围/预算/关键计划时适用变更已批准并生效，否则禁止提交解决 |
| BUG | 新建→待修复；反馈开工→修复中；提交修复→待复测 | 有权发起人；责任人或获授权主PM填修复结果/版本/时间 |
| 需求/BUG | 待验证/待复测→已关闭；退回→开发中/修复中 | 仅原发起人；确认评价必填，保存实际解决/修复信息及独立关闭时间；代理规则待Q2 |
| 问题 | 新建→待解决；反馈→处理中；提交解决→已解决 | 主PM登记（按当前权限基线）；责任人或主PM提交措施和结果 |
| 问题 | 已解决→已关闭；退回→处理中 | 仅该项目主PM，持续督办至最终关闭 |
| 风险 | 新建→监控中；反馈/评估/策略调整保持监控中 | 主PM登记；主PM/PMO评估；责任人/主PM维护应对，权限须接策略 |
| 风险 | 监控中→已缓解 | 当前实现责任人/主PM；建议必须有措施及评价，是否终态/需PM复核待Q3 |
| 风险 | 监控中→已转问题，同时新增待解决问题 | 仅主PM；发生时间/说明必填；保留原风险，显式映射等级/责任人/来源，不整包复制meta |
| 通用 | 转办：通常不改处理状态；反馈追加历史；升级不改主状态 | 可处理责任人/主PM；督办PM/PMO或配置规则驱动。待确认节点转办是否退回处理待Q4 |
| 终态 | 已关闭禁止编辑；已缓解/已转问题仅允许经确认的动作集 | 不允许靠feedback恢复状态；无重开/撤销原文时不增加默认按钮 |

不新增单独“审批中工单”替代变更事实；需要展示时用派生标签“等待关联变更生效”。同理超期、升级层级、待谁办理、可用按钮由状态+角色+公共selector派生。

### 5.3 store与跨模块接入

1. 页面只保留草稿/Modal/URL筛选，读取`useBusinessStore`和公共selector，调用`dispatch(action, actor)`。
2. `dispatch`继续先`assertActionAccess`，`transition`克隆并校验对象、状态、归档等，再交给事项领域处理。直接领域调用也必须校验业务角色和状态，不能仅依赖按钮禁用。
3. 沿用create-ticket/update-ticket/risk-to-issue，按契约扩展结构化payload；评估、附件引用、升级等若需新action由协调者统一增加。不要恢复close-bug/close-issue旁路。
4. 一次transition原子完成原单更新、历史、来源关联及必要决策记录；失败保留原业务状态，store仍可追加拒绝审计。事项创建后的真实ID不得由页面用数组长度预测，协调者需提供可靠的提交结果/创建定位契约。
5. 建议公共selector契约：`selectTicketView`、`selectTicketList`、`selectTicketCounts`、`selectTicketAllowedOperations`、`selectTicketAssignableUsers`、`selectTicketEscalation`；名称为拟议，实施前冻结参数/返回值。过滤顺序先权限/项目范围，再业务筛选/统计/分页，计数不泄露不可见类型。
6. 待办用同一当前责任/确认人/升级规则；升级决策按源事项+级别+规则版本去重。领导审批结果回链原风险，不能将“已决策”投影为“已关闭风险”。
7. 日报新建调用同一事项创建逻辑再关联ID；质量/验收引用原事项处理结果；事项解决不直接批准验收。报告历史快照保留，当前统计重新取源对象。
8. 归档包含meta/轨迹/附件版本依据并由统一归档门禁锁住建设事实；运维仅引用来源，不能解锁建设期事项或把运维成本计入工单。
