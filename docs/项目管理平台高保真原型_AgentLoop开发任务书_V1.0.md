# 0. Agent 执行总原则

本任务不是“搭一个页面框架”或“做几个示例页”，而是要持续 Loop，最终形成一套**覆盖全部业务页面、数据关系一致、可用于产品评审和客户演示的高保真项目管理平台原型**。

Agent 必须遵循以下规则：

1. **不得在只完成首页、看板或若干核心页面后停止。**
2. 必须实现本文列出的全部页面编号，并保证均可从系统导航、关联对象或路由直接访问。
3. 禁止用“TODO”“Coming Soon”“建设中”“占位页”代替未完成页面。
4. 页面不要求真实业务能力，但必须具备足够的前端交互，使原型能够完成完整演示。
5. 所有业务数据均使用 Mock Data，但必须丰富、真实、前后一致，而不是随机的“张三/项目A”式演示数据。
6. 相同项目在领导驾驶舱、项目经理工作台、项目详情、预算、核算、验收、结算等页面中的金额、状态、里程碑、问题数量必须保持一致。
7. 任何 Mock 规则阈值都只作为**演示配置**存在，不得表述为最终业务制度。
8. 如果三份上游文档存在描述差异，优先级按照：
   - 页面清单与原型设计说明 V1.1
   - 详细功能清单 V1.1
   - PRD V1.1
9. 未明确的 UI 细节由 Agent 按专业 ToB SaaS 产品习惯自行补齐，不要因为非关键视觉细节反复向用户确认。
10. 每轮开发完成后必须执行质量检查，修复后再进入下一轮。

# 1. 项目目标

## 1.1 产品目标

构建一套以“四算”为经营主线、以项目阶段为过程主线、以项目基线为控制主线的企业级项目全生命周期管理高保真原型。

- 商机与概算；
- 项目立项；
- WBS / 里程碑；
- 项目预算；
- 未签立项；
- 项目执行；
- 日报 / 周报；
- 需求 / BUG；
- 问题 / 风险；
- 工时与人力成本；
- 采购 / 外包 / 项目费用；
- 动态核算；
- 项目变更；
- 阶段切换；
- 内部验收；
- 供应商验收；
- 客户验收；
- 项目报验；
- 项目结算；
- 四算分析；
- 项目经营结果；
- 后评价与资料归档；
- 运维衔接；
- 项目经营驾驶舱；
- 项目组合分析；
- 项目异常中心；
- 领导待决策事项；
- 配置与管理。

## 1.2 演示目标

最终原型应能支持至少以下两条完整演示路线。

### 演示路线 A：项目经理视角

> 项目经理工作台  
> → 进入某在建项目  
> → 查看 WBS / 里程碑  
> → 查看成本与动态核算  
> → 查看问题风险  
> → 发起项目变更  
> → 查看阶段切换  
> → 进入客户验收  
> → 查看项目结算与四算结果。

### 演示路线 B：管理层视角

> 项目经营驾驶舱  
> → 查看全局项目规模与经营指标  
> → 查看高风险项目  
> → 下钻某项目  
> → 查看风险原因  
> → 查看四算偏差来源  
> → 查看待决策事项  
> → 跳转关联的变更 / 风险 / 预算事项。

# 2. 明确不做的内容

本阶段是**高保真原型开发**，以下能力明确不建设真实实现：

- 不建设 Java / Go / Node 等服务端；
- 不建设真实数据库；
- 不建设真实登录认证；
- 不接真实 OA / ERP / CRM / HR / 财务 / 采购系统；
- 不发送真实邮件、短信、钉钉消息；
- 不上传真实文件到服务器；
- 不做真实支付、合同签章、开票、回款；
- 不做真实审批引擎；
- 不做真实权限服务；
- 不要求真实 Excel/PDF 导出；
- 不要求真实大数据计算；
- 不做生产部署架构。

但为了高保真演示，可以在浏览器内模拟：

- 查询；
- 筛选；
- Tab 切换；
- 分页；
- 排序；
- 展开收起；
- Drawer / Modal；
- 表单校验；
- 状态切换；
- 审批通过 / 驳回；
- 新增一条临时 Mock 记录；
- “上传”本地文件名；
- 点击 KPI 下钻；
- 页面间跳转；
- 模拟加载；
- 成功 / 警告 / 错误提示；
- Mock 数据实时重新计算。

所有上述行为只需要在前端内存中生效，刷新页面后是否恢复初始数据不做强制要求。

# 3. 技术栈

## 3.1 基础技术栈

必须使用：

- **React 18+**
- **TypeScript**
- **Vite**
- **Ant Design 5.x**
- **React Router 6+**
- **dayjs**
- **@ant-design/icons**

推荐：

- **@ant-design/charts**：经营驾驶舱及专题分析图表；
- **Zustand**：仅用于全局演示态、当前角色、全局筛选、临时表单变更；
- **lodash-es**：仅在确有必要时使用。

不建议引入：

- 重型后端框架；
- Redux Toolkit（本项目无复杂真实业务状态）；
- UI 体系与 Ant Design 重叠的其他组件库；
- 大量仅用于装饰的动画库。

## 3.2 包管理器

- 如果现有仓库已经存在 lock 文件，保持原包管理器；
- 如果是空仓库，默认使用 `pnpm`。

## 3.3 基础命令

项目至少支持：

```bash
pnpm dev
pnpm build
pnpm lint
pnpm typecheck
```

如现有模板已经将 typecheck 合并至 build，可在 README 中说明。

# 4. UI / UX 总体规范

## 4.1 产品风格

整体定位：

> **专业、稳重、信息密度高、适合大型集团项目管理场景的 ToB SaaS。**

避免：

- 大量渐变；
- 过度卡通；
- 夸张动画；
- 过多大圆角；
- 大面积空白；
- 每块内容都做成独立“卡片墙”；
- 为视觉而视觉的图表。

优先：

- 清晰层级；
- 强信息结构；
- 表格与详情密度适中；
- 状态颜色统一；
- 可下钻；
- 可解释；
- 可追溯。

## 4.2 基础布局

桌面端优先：

- 设计基准：1440 × 900；
- 最低适配宽度：1280；
- 左侧导航：220~240px；
- 顶部 Header：56~64px；
- 内容区域使用自适应宽度；
- 复杂表格允许横向滚动；
- 不要求移动端高保真。

推荐结构：

```text
┌──────────────────────────────────────────────────────┐
│ Logo / 系统名称       全局搜索     角色切换 / 用户   │
├──────────────┬───────────────────────────────────────┤
│              │ 面包屑 / 页面标题 / 页面操作          │
│ 左侧菜单      ├───────────────────────────────────────┤
│              │                                       │
│              │              页面内容                  │
│              │                                       │
└──────────────┴───────────────────────────────────────┘
```

# 7. 全局 Mock Data 设计

Mock 数据不是“填页面”的附属内容，而是整个高保真原型的重要组成部分。

## 7.1 数据要求

Mock 必须：

- 中文真实语义；
- 项目名称接近真实政企项目；
- 金额、时间、阶段、状态互相合理；
- 同一个项目跨页面保持一致；
- 有正常项目，也有明显异常项目；
- 有不同项目类型；
- 有不同项目金额层级；
- 有不同组织、区域；
- 有已签、未签；
- 有盈利项目、低毛利项目、预测亏损项目；
- 有提前投入；
- 有采购、外包、人力、差旅等成本；
- 有风险问题、需求、BUG；
- 有已验收、结算、运维、关闭项目；
- 有完整历史版本。

建议使用固定 seed 生成，刷新后不变化。

至少包含：

| 数据对象 | 最低数量 |

| 合同 | 45 |
| 概算版本 | 80 |
| 预算版本 | 80 |

## 7.4 四算数据一致性公式

建议所有项目统一按照以下 Mock 逻辑计算：

```text
概算成本 = 售前阶段各成本科目预计值合计

预算成本 = 当前生效预算版本各成本科目合计

已发生成本 = 已发生人力 + 已发生采购 + 已发生外包 + 已发生费用

已承诺成本 = 已签未结的采购 / 外包等承诺成本

滚动预测成本
= 已发生成本
+ 已承诺成本
+ 剩余阶段预计成本

预算偏差
= 滚动预测成本 - 预算成本

预测毛利
= 当前项目收入 - 滚动预测成本

预测毛利率
= 预测毛利 / 当前项目收入

结算毛利
= 最终项目收入 - 结算实际成本
```

所有页面必须引用统一 helper / selector 计算，禁止每个页面写一套公式。

## 7.5 项目健康度 Mock 规则

业务正式规则未定，原型可使用“演示配置”。

示例：

### 高风险

满足任一：

- 关键里程碑延期 ≥ 30 天；
- 滚动预测成本超预算 ≥ 15%；
- 存在重大风险 / 重大问题；
- 预测毛利率低于演示阈值；
- 回款严重逾期。

### 预警

满足任一：

- 关键里程碑延期 7~29 天；
- 成本执行率明显偏高；
- 毛利下降；
- 重要问题持续未关闭；
- 未签立项投入接近上限。

### 关注

- 里程碑 14 天内到期；
- 成本执行率接近阶段预算；
- 存在一般风险；
- 存在需要关注但未达到预警的事项。

### 健康

未命中以上条件。

页面必须提供“为什么被判定为当前健康度”的解释。

# 17. 质量规范

## 17.1 TypeScript

禁止：

- 大面积 `any`；
- 为绕过报错使用 `@ts-ignore`；
- 未使用变量大量残留；
- 类型定义与数据不一致。

## 17.2 React

禁止：

- 巨型单文件塞全部页面；
- 复制粘贴大量重复组件；
- 在 render 中重新随机生成 Mock；
- 直接在多个页面重复经营计算逻辑。

## 17.3 Console

最终不得存在明显：

- React key warning；
- uncontrolled / controlled warning；
- Router warning；
- AntD 严重 warning；
- 未捕获 Promise；
- 运行时报错。

## 17.4 文案

全部 UI 使用中文。

禁止：

- Lorem ipsum；
- Project A；
- User 1；
- Test Data；
- “这里放图表”；
- “待补充”。

# 22. Agent 停止条件

Agent 不应因为以下原因停止：

- “主页面已经完成”
- “核心流程已经实现”
- “剩余页面类似”
- “后续可以补充”
- “Mock 数据已经足够”
- “主要功能已经能演示”

只有满足第 21 章全部 Definition of Done 才能停止 Loop。

如果遇到非阻塞性需求缺口：

1. 参考 ToB SaaS 常规交互补齐；
2. 在 `DEV_PROGRESS.md` 中记录假设；
3. 继续开发。

只有以下情况可以请求人工确认：

- 三份上游文档对同一核心业务规则存在直接冲突，且会改变整体页面架构；
- 缺少必须的业务概念，无法继续构造合理原型；
- 用户明确要求改变技术栈或整体产品方向。

# 23. 最终交付目标

最终结果应该让产品经理打开项目后，可以直接进行如下工作：

- 向主管展示完整产品方案；
- 向业务部门讲解项目全生命周期流程；
- 向客户演示概算、预算、核算、结算四算体系；
- 从领导驾驶舱下钻异常项目；
- 从项目经理工作台演示项目执行；
- 讨论页面字段、交互和业务规则；
- 基于该高保真原型继续进入正式研发需求拆分。

最终原型的标准不是“能跑”，而是：

> **看起来已经像一套完整的企业级项目管理 SaaS，只是所有数据和业务动作仍然运行在前端 Mock 环境中。**
