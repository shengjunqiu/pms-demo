## 1. 高优先级：日报 + 周报合并

### 现状分析

- **页面文件**: `src/pages/execution/ReportsPage.tsx`（47 行）
- **路由**: `/projects/:id/daily-reports`（HS-03）和 `/projects/:id/weekly-reports`（HS-04）
- **组件**: 同一个 `ReportsPage` 组件，通过 `weekly` prop 区分日报/周报
- **数据模型**: `dailyReports: DailyReport[]` 和 `weeklyReports: WeeklyReport[]` 两个独立数组
- **状态管理**: `save-daily` 和 `save-weekly` 两个独立 dispatch action
- **页面结构**: 两个页面共享 90% 的 UI 结构（PageHeader、Alert、PageSection、Drawer、Modal）

### 冗余表现

1. 日报和周报本质都是"项目定期报告"，只是周期不同
2. 周报内容由日报聚合而来，数据源高度重叠
3. 两个页面共享同一组件文件，但路由和菜单入口分开
4. 用户需要在日报和周报之间来回切换查看

### 优化方案

**目标**: 将日报/周报合并为统一的"项目报告"页面，用 Tab 切换周期

**具体步骤**:

1. **合并路由**: 将 `/projects/:id/daily-reports` 和 `/projects/:id/weekly-reports` 合并为 `/projects/:id/reports`
2. **统一组件**: 在 `ReportsPage.tsx` 中添加 Tab 切换（日报/周报），替代当前通过 `weekly` prop 和路由参数区分的方式
3. **合并数据模型**: 考虑将 `DailyReport` 和 `WeeklyReport` 统一为 `ProjectReport` 类型，增加 `period` 字段（`daily` | `weekly`）
4. **统一 dispatch**: 将 `save-daily` 和 `save-weekly` 合并为 `save-report`，通过 `period` 参数区分
5. **菜单合并**: 在项目详情页中将"日报"和"周报"两个菜单项合并为"项目报告"

### 影响范围

| 文件 | 改动类型 |
|------|----------|
| `src/pages/execution/ReportsPage.tsx` | 重构（添加 Tab 切换） |
| `src/mock/business-domain.ts` | 数据模型合并 |
| `src/mock/reports.ts` | 工具函数调整 |
| `src/routes/modules/execution.tsx` | 路由合并 |
| `src/routes/manifest.ts` | 菜单项合并 |
| `src/routes/navigation.ts` | 导航调整 |

### 验收标准

- [ ] 日报和周报可在同一页面通过 Tab 切换
- [ ] 日报填报和周报上报功能正常
- [ ] 历史日报和周报数据可正常查看
- [ ] 所有引用旧路由的地方正确跳转到新路由

## 2. 高优先级：采购 / 外包 / 费用三入口合并

### 现状分析

- **页面文件**: `src/pages/execution/CostSourcesPage.tsx`（54 行）
- **路由**: `/projects/:id/procurement`（HS-10）、`/projects/:id/outsourcing`（HS-11）、`/projects/:id/expenses`（HS-12）
- **组件**: 同一个 `CostSourcesPage` 组件，通过 `kind` prop 区分（`procurement` | `outsource` | `expense`）
- **数据模型**: 统一使用 `costOrders: CostOrder[]` 数组，通过 `kind` 字段区分
- **状态管理**: 统一使用 `submit-cost-order` 和 `process-cost-order` dispatch action
- **页面结构**: 三个入口共享 95% 的 UI 结构和业务逻辑

### 冗余表现

1. 采购、外包、费用本质都是"成本申请"，只是科目类型不同
2. 三个页面共享同一组件文件，但路由和菜单入口分开
3. 用户需要分别进入三个页面查看成本，无法在一个视图中看到全部成本
4. 项目详情页中三个菜单项占用过多空间

### 优化方案

**目标**: 将采购/外包/费用合并为统一的"成本管理"页面，用 Tab 切换类型

**具体步骤**:

1. **合并路由**: 将三个路由合并为 `/projects/:id/costs`，通过 URL query 参数 `?kind=procurement` 区分
2. **统一组件**: 在 `CostSourcesPage.tsx` 中添加 Tab 切换（采购/外包/费用）
3. **添加汇总视图**: 在 Tab 上方添加一个汇总卡片，显示三种成本的总额和占比
4. **菜单合并**: 在项目详情页中将三个菜单项合并为"成本管理"

### 影响范围

| 文件 | 改动类型 |
|------|----------|
| `src/pages/execution/CostSourcesPage.tsx` | 重构（添加 Tab 切换 + 汇总视图） |
| `src/routes/modules/execution.tsx` | 路由合并 |
| `src/routes/manifest.ts` | 菜单项合并 |
| `src/routes/navigation.ts` | 导航调整 |

### 验收标准

- [ ] 采购/外包/费用可在同一页面通过 Tab 切换
- [ ] 顶部显示三种成本的汇总统计
- [ ] 新建申请时自动选择当前 Tab 对应的类型
- [ ] 所有引用旧路由的地方正确跳转到新路由

## 3. 中优先级：未签立项台账合并到项目台账

### 现状分析

- **页面文件**: `src/pages/unsigned/UnsignedProjectsPage.tsx`（10 行）+ `UnsignedProjectPage.tsx`（22 行）+ `StartConfirmationPage.tsx`（248 行）
- **路由**: `/unsigned-projects`（YS-13）和 `/unsigned-projects/:id`（YS-14）
- **数据**: `unsignedProjects: Record<string, UnsignedProjectControl>` 存储在 BusinessState 中
- **关系**: 未签项目本质上是 `Project` 的一个状态（`isUnsigned` 字段），但被独立为一个完整的台账模块

### 冗余表现

1. 未签项目是项目生命周期的一个阶段（合同未签），但被独立为一个完整的台账
2. 项目详情页（`/projects/:id`）和未签项目详情页（`/unsigned-projects/:id`）有大量重叠信息
3. 未签项目的"签约进展"、"投入成本"等信息可以在项目详情页中以 Tab 形式展示
4. 用户需要在项目台账和未签台账之间来回切换

### 优化方案

**目标**: 将未签立项台账合并到项目台账中，作为项目列表的一个筛选维度

**具体步骤**:

1. **项目列表添加筛选**: 在项目台账（`/projects`）中添加"未签项目"筛选维度
2. **项目详情添加 Tab**: 在项目详情页中添加"未签管控"Tab，包含当前未签详情页的所有功能
3. **保留独立路由（可选）**: 保留 `/unsigned-projects` 作为快捷入口，但数据源统一
4. **合并数据**: 将 `unsignedProjects` 中的信息合并到 `Project` 类型中，或作为关联数据

### 影响范围

| 文件 | 改动类型 |
|------|----------|
| `src/pages/projects/ProjectListPage.tsx` | 添加未签筛选 |
| `src/pages/projects/ProjectDetailPage.tsx` | 添加"未签管控"Tab |
| `src/pages/unsigned/UnsignedProjectsPage.tsx` | 简化或移除 |
| `src/pages/unsigned/UnsignedProjectPage.tsx` | 简化或移除 |
| `src/mock/business-domain.ts` | 数据模型调整 |
| `src/routes/manifest.ts` | 菜单项调整 |

### 验收标准

- [ ] 项目列表可按"未签"状态筛选
- [ ] 项目详情页可查看未签管控信息
- [ ] 签约进展更新、追加投入、合同签订确认等功能正常
- [ ] 旧路由 `/unsigned-projects` 可重定向或保留为快捷入口

## 5. 低优先级：变更六类型简化为三种

### 现状分析

- **变更类型**: `'范围变更' | '工期变更' | '成本变更' | '资源变更' | '合同变更' | '综合重大变更'`
- **定义位置**: `src/models/types.ts` 中 `ProjectChange.type` 字段
- **页面**: `src/pages/changes/ChangeFormPage.tsx`（524 行）
- **数据**: `changes: ProjectChange[]` 和 `changeRequests: ChangeRequest[]`

### 冗余表现

1. 六种变更类型中，部分类型在审批流程上高度相似：
   - 范围变更和工期变更通常一起发生，审批路径相同（PMO 审批）
   - 成本变更和资源变更通常一起发生，审批路径相同（财务 + PMO）
   - 合同变更通常触发综合重大变更审批（PMC 决策）
2. 六种类型导致变更表单过于复杂，用户选择困难
3. 实际业务中，变更往往同时影响多个维度

### 优化方案

**目标**: 将六种变更类型简化为三种

**具体步骤**:

1. **简化类型定义**: 将 `ProjectChange.type` 改为：
   - `'范围/进度变更'` — 合并原"范围变更"和"工期变更"
   - `'成本/资源变更'` — 合并原"成本变更"和"资源变更"
   - `'合同/综合变更'` — 合并原"合同变更"和"综合重大变更"
2. **更新表单**: 在 `ChangeFormPage.tsx` 中更新类型选择器
3. **更新审批规则**: 确保三种类型的审批路径正确
4. **数据迁移**: 历史数据保留原类型，新数据使用新类型

### 影响范围

| 文件 | 改动类型 |
|------|----------|
| `src/models/types.ts` | 类型定义修改 |
| `src/models/changes.ts` | ChangeInput 类型调整 |
| `src/pages/changes/ChangeFormPage.tsx` | 表单更新 |
| `src/mock/changes.ts` | 审批规则调整 |
| `src/mock/business-domain.ts` | 变更处理逻辑调整 |

### 验收标准

- [ ] 新建变更时只有三种类型可选
- [ ] 三种类型的审批路径正确
- [ ] 历史变更数据可正常查看（保留原类型）
- [ ] 变更台账和详情页正确显示类型

## 6. 低优先级：四算科目 + 成本基准配置合并

### 现状分析

- **页面文件**: `src/pages/configuration/FinanceConfigurationPage.tsx`（28 行）
- **路由**: `/settings/cost-mapping`（CF-04）和 `/settings/cost-baseline`（CF-05）
- **组件**: 同一个 `FinanceConfigurationPage` 组件，通过 `kind` prop 区分（`subjects` | `rates` | `alerts`）
- **数据模型**: `financeConfiguration: FinanceConfigurationState` 包含三个子配置

### 冗余表现

1. 四算科目映射（CF-04）和成本基准配置（CF-05）都是财务配置，共享同一组件

**具体步骤**:

2. **统一组件**: 在 `FinanceConfigurationPage.tsx` 中添加三个 Tab（科目映射/成本基准/预警规则）
3. **菜单合并**: 在配置菜单中将三个项合并为"财务配置"

## 实施路线图

| 优先级 | 优化项 | 预估工作量 | 风险 | 建议批次 |
|--------|--------|------------|------|----------|
| 高 | 日报+周报合并 | 2-3 天 | 低（组件已共享） | 第一批 |
| 高 | 采购/外包/费用合并 | 2-3 天 | 低（组件已共享） | 第一批 |
| 中 | 未签台账合并 | 3-4 天 | 中（涉及页面较多） | 第二批 |
| 中 | 四台账合并 | 2-3 天 | 低（组件已共享） | 第二批 |
| 低 | 变更类型简化 | 1-2 天 | 中（影响数据模型） | 第三批 |
| 低 | 财务配置合并 | 1-2 天 | 低（组件已共享） | 第三批 |

### 并行开发建议

- **第一批（高优先级）**: 两个优化项互不依赖，可并行开发
  - 开发者 A: 日报+周报合并
  - 开发者 B: 采购/外包/费用合并
- **第二批（中优先级）**: 两个优化项互不依赖，可并行开发
  - 开发者 A: 未签台账合并
  - 开发者 B: 四台账合并
- **第三批（低优先级）**: 两个优化项互不依赖，可并行开发
  - 开发者 A: 变更类型简化
  - 开发者 B: 财务配置合并
