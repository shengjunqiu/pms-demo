## 3. 开工前公共接口任务

以下是需要实现并验证的设计决定，当前代码尚不满足全部要求。主协调者在首批页面开工前确定接口和初值；语义改动可分小批交付，相关业务包在依赖版本合入后接续。公共任务不另计页面，也不虚构新的 FND 验收项。

### P0-1：统一状态与领域接入

沿用现有 `useBusinessStore → dispatch(action, actor) → transition`。领域模块导出 `XxxAction` 和 `applyXxxAction(state, action, actor)`，处理 `transition` 已克隆的状态并返回审计目标 ID；失败不产生局部更新。当前 `cost-orders.ts`、`deliverables.ts` 可作为结构参考。

新增商机、方案评审、提前投入、规划草稿、验收轮次、报验、结算申请、运维周期和规则版本等实体时，统一接入 `BusinessState` 与初始化函数。领域类型可放独立模型文件，公共 `Project/BudgetVersion/BaselineVersion` 的兼容扩展由主协调者处理。

页面的 Form 草稿和筛选可用局部状态，已保存业务事实必须进入统一 Store。页面不直接改项目汇总；领域动作完成后以统一规则维护流水、版本和摘要。应用期 selector 显式接收当前业务状态，不能从导入的静态 Mock 读取已可修改的业务事实。

### P0-2：版本引用、预算审批与基线

现状：`selectFourCalculations` 和预算提交按首个 `isFrozen` 概算取值；`review` 对预算批准后立即激活预算与基线；预算提交要求已有生效基线。这不能完整覆盖 GS 多版本与 YS 新项目首次预算。

设计约定：

- 商机有当前概算引用；立项申请及正式项目绑定选定的冻结概算 ID，不能随商机“最新版本”漂移。审批保存提交时概算、计划、预算、规则快照。
- 基线包含范围、WBS、里程碑、资源及成本的完整快照和来源版本 ID；执行只使用当前有效基线，规划草稿独立保存。
- **预算审批通过 → 待 PMO 基线确认 → 完整基线生效**。确认前旧项目仍使用旧有效版，新项目保持未启动；确认时重新校验引用、计划评审、项目锁定与权限，再原子切换版本。
- 明确首次预算、既有项目预算审批和项目变更的业务类型。HS 项目变更经其分级审批通过可追加统一基线；不能用一次通用 `review` 隐式混同两套流程。
- 已有 `kind: budget` 审批和“通过并生效”界面随真实语义调整，不能为保住旧测试将全部历史预算审批改名为“项目变更”。待决策处理后移出原待审，PMO 确认产生对应新待办。
- `/approvals/:id` 与 YS-11 标准入口解析同一真实审批单；项目有多张审批时明确选择单据。项目 ID 和审批 ID 不混用，不复制审批流程。

优先建立一个合法规划期演示对象，覆盖未形成生效基线的新项目；P-001 等固定故事继续覆盖冻结后的只读和变更入口。禁止把已生效 V0.9/V1 基线当草稿任意修改。

必须回归：GL-06→原预算审批→WK-02→PMO 确认→HS-01/13；预算审核期间上游变化不改提交快照；GS 多个冻结概算仍能复算对应项目四算；HS-02/16/17 仍使用正确的有效快照。

### P0-3：结算冻结与成本入口

现状：`settle` 由财务直接形成最终结算并锁定，没有结算申请中的冻结阶段。

设计约定：

- `可编制 → 已提交/审核中 → 补充整改或确认锁定`。提交先检查客户最终验收、待决成本和重复结算，再保存建设成本/收入/版本快照并冻结建设成本入口。
- 所有相关工时、采购、外包、费用、成本确认及预算/变更动作共用建设期可写校验；页面只读和领域拒绝同时生效。
- 演示默认：材料补充不解冻金额；锁定前如需金额调整，由财务退回并说明原因，解除本申请的临时冻结，再经原成本业务修正、重新提交形成新快照。已有最终锁定不因此解除，旧申请和差异保留。
- 财务/PMO确认后冻结最终结果，重复确认不重复计费；运维按独立周期及成本集合记录。
- 结算完成不自动等同项目关闭。当前 `settle` 将 `phase` 设为“已关闭”的行为需调整；JS-13仍检查归档、后评价、未结事项和运维状态后才关闭。

必须回归：HS-09/10/11/12/13、成本确认、YS预算/HS变更、GL-02/06、JS结算/运维，验证所有入口无法绕过冻结且运维不污染历史结算。

### P0-4：合同、回款、前期成本与规则

现状：回款 selector 与健康重算仍读静态 `mockContracts/mockReceiptPlans`；阶段规则和健康阈值目前为固定演示常量。

- 合同与回款计划需要可变时统一接入业务状态，所有项目、GL 汇总和健康度读取相同集合。实收明细/汇总同源，按合同 ID 去重，未签拟签金额不计已签额。
- GS投入保留商机与来源单据ID；转项目关联并继承原成本一次，额度审批不直接制造实际成本，承诺转实际保持互斥。
- 主协调者先约定规则版本、组织/类型适用范围、生效日、启停及命中原因的读取接口，保留当前演示值作为初始版本。CF 页面后续只维护这套配置。
- 新提交采用适用规则版本，历史审批/预算/基线/工时单价保持快照。CF 预警规则发布可重算当前演示预警；不能静默改写历史结算或原审批路径。

必须回归：P-001四算基准、P-004未签→签约口径、GS→YS成本继承、JS实收→GL回款指标、健康筛选与下钻同范围；CF发布后新业务命中、历史业务不漂移。

### P0-5：路由接入与回归入口

各域按 catalog 导出自己的页面实现映射，主协调者在统一入口聚合；每个标准页面只注册一次，有实现时不再同时生成占位路由。保留现有原审批附加路由，通过同一对象ID连接标准入口。可以小范围替换当前长字符串排除表，不重做整个导航系统。

主协调者准备 `e2e/`、独立 Playwright 配置和真实 `test:e2e`。Vitest 的领域测试范围与 E2E 目录明确分离，防止现有 `vitest run` 误收集浏览器测试；端口及 fixture 重置由统一测试入口管理。具体工具使用遵循对应技能与环境能力。

## 5. 首批调度与关键路径

首批开发为 A01（4页）、B01（3页）、C01（4页）。主协调者先处理 P0 接口、规划期fixture、各域可编译接入点和工作目录分配，再按已就绪依赖释放开发包。P0接口可分批发布，避免等待全部公共任务才开展可独立工作。

- A01先完成商机录入、评估和详情整合；九类Tab及转立项未齐时作为已集成待验收，A继续A02～A04，B同步实现B04立项接收。
- B01用规划草稿测试编辑与评审，用已有冻结项目测试只读和变更。B02、B03接续后正式验证完整计划/基线/变更链；不能为了首批通过解除固定故事的基线冻结。
- C01把JS-04一同实现，统一客户验收与报验金额。若结算下钻仍未齐，可先正式验收确实独立闭环的JS-01/02，其他页待C02合入后验收。
- 单包交付后优先继续本业务链、解除已集成页面的下钻依赖（例如A01之后优先A02）。本业务线已交付，或后续包确有外部阻塞且无可推进的关键依赖时，再接D01～D03；每个配置包明确唯一负责人，同一配置模块不由多人同时改写。主协调者持续处理合入与M01，结束阶段将空闲开发者转为只读回归/证据审查。

关键依赖是“概算冻结→立项→计划预算基线→启动/变更”和“验收→报验→结算冻结→归档/运维/关闭”。已有项目支持后半段先开发；全链演示仍须接上真实来源，不能用跨阶段随意改状态代替。

## 6. 可执行的委派内容

主协调者委派时使用以下字段结构，填入当次真实值，不将示例路径或未确认fixture作为事实：

```text
任务：本次只实现指定包及其页面，不运行正式 Loop，不继续委派。
上下文：仓库内 AGENTS.md、pms-prototype-loop、catalog 中本包条目及对应原文。
目录：指定的绝对 workdir、独立分支、base_commit、contract_commit。
范围：包ID、精确页面ID、owned_paths白名单、由协调者提供的共享接口提交。
依赖：实现前置已具备项、正式验收仍缺的目标及负责者。
场景：真实对象ID/创建步骤，正常、阻断、角色、版本和跨页同步。
交付：代码提交/补丁、共享改动清单、检查命令/退出码、实际观察与未解决依赖。
```
